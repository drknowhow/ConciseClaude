# 6.1 and 6.2 benchmarks, 2026-10-15

## 6.2: cheaper than default on both models

The 6.1 run below found the plugin dearer than default on Sonnet. Its rule
text added about 2,950 input tokens to every session (6,980 against 4,033
cache-write tokens on a cold call), and in short or tool-heavy sessions that
outweighed the shorter replies. 6.2 keeps the rules but halves the text and
drops the session-start pointer, which subagents never see. The overhead is
now about 1,225 tokens, and an attribution run put about 1,160 of the 6.2
total on the style and 290 on the pointer before it went.

Default against 6.2, every case run twice (232 turns, $23.64; Sonnet re-run
after the pointer was removed, 116 turns, $7.15):

| | Opus | Sonnet |
|---|---:|---:|
| Median reply prose, single-turn | 574 vs 1,610 (−64%) | 597 vs 1,522 (−61%) |
| Output tokens, all but depth | −48% | −36% |
| Wall time, all but depth | −34% | −22% |
| **Cost, all but depth** | **−23%** | **−13%** |
| Six-turn conversations, ops and design | −33%, −53% | −17%, −33% |
| Six-turn coding session | 0% | −1% |
| Single cold calls | +5% | +9% |
| Key points covered (default) | 87% (98%) | 83% (95%) |

The Opus column comes from the run with the pointer still in place, so it
understates 6.2's saving slightly. Coverage was graded blind on the same
rubric as below; 6.1 scored 82% across both models and 6.2 85%. Every 6.2
reply opened with its status tag (6.1: 89% on Opus, 28% on Sonnet), and the
meter counted under one bold span per reply against 8 to 9 for default.

A separate test ran the six-turn coding session three times per arm on
Sonnet. Before the pointer was removed, 6.2 cost 6 to 7% more than default
there and made 66 to 68 tool round trips against 50 to 59; without the code
rules it made 49. Moving the comment rule into the style didn't reduce the
round trips. After the pointer went, the full benchmark put coding at −1%.

Single cold calls still cost more, because writing the style to the prompt
cache costs more than one short reply saves. In a real session the system
prompt is several times larger than in this headless test, so the fixed
overhead is a smaller share, and the saving grows with every turn.

## Haiku 5.5

6.2 told Haiku to ignore the style and its hooks stood down for Haiku, as
5.1 found no saving there. Haiku still pays for the rule text, and it half
followed the style anyway. The same benchmark on Haiku 5.5, every case run
twice ($1.16 in all), compared that with a variant where Haiku gets the
whole rule set, which is what 6.3 ships:

| Against default | 6.2 (Haiku told to ignore) | 6.3 (whole rule set) |
|---|---:|---:|
| Cost, all but depth | +10% | 0% |
| Output tokens | −10% | −23% |
| Six-turn conversations, ops and design | −15%, −10% | −25%, −10% |
| Six-turn coding session | +45% | +21% |
| Single cold calls | +11% | +7% |
| Replies opening with the status tag | 61% | 100% |
| Key points covered (default 90%) | 87% | 84% |

One grader scored all three arms, 20 replies each, so differences of a few
points are within noise. Most of Haiku's output is hidden thinking, which
the style doesn't shorten, so on Haiku the shorter replies only pay for the
rule text.

## 6.1

This run checks what 6.0 and 6.1 changed: a 600-character budget instead of
400, plain-word status tags instead of glyphs, the plain-writing rules, and
the code and repo-text rules. It compares no plugin (default) with 6.1.1 on
Opus 5.5 and Sonnet 5.5, using headless Claude Code with `--plugin-dir`.
Each model ran `bench/ab.py`'s eight questions plus a depth question and a
PR-description draft, twice each, the slugify coding task twice, and the
three six-turn conversations once: 160 turns. A 5.1.0 control arm ran the
single-turn questions only. The runs cost $17.21 at API-rate estimates.

Replies were graded blind by Sonnet subagents against 6 to 8 key points per
question, written by a separate subagent before any replies existed. Status
tags and glyphs were stripped from the first line so the grader couldn't
tell the arms apart.

| | Opus default | Opus 6.1 | Sonnet default | Sonnet 6.1 |
|---|---:|---:|---:|---:|
| Median reply prose, single-turn | 1,654 | 606 (−63%) | 1,508 | 524 (−65%) |
| Output tokens, all but depth | | −47% | | −25% |
| Wall time, all but depth | | −38% | | −16% |
| Cost, all but depth | | −8% | | +9% |
| Depth question, output tokens | 6,016 | 6,364 | 3,890 | 5,889 |
| Bold spans per reply | 9.1 | 0 | 7.0 | 0 |
| Comment lines in code written | 1 of 283 | 3 of 260 | 0 of 212 | 0 of 213 |

Cost depends on the work:

| | Opus | Sonnet |
|---|---:|---:|
| Six-turn conversations, ops and design | −31%, −50% | −11%, −19% |
| Six-turn coding session | +26% | +19% |
| Single cold calls | +28% | +43% |

The plugin saves where replies dominate the bill, in conversation. In a cold
call, writing the longer style text to the prompt cache costs more than the
shorter reply saves. In coding, the code rules join the context on the first
edit and tool output dominates. Each conversation ran once, so treat the
per-conversation figures as rough.

## Coverage

| Arm | Key points covered | Too terse | Clarity (1-5) | Factual errors |
|---|---:|---:|---:|---:|
| Default | 97% | 0 of 40 | 4.9 | 1 |
| 5.1.0 | 78% | 0 of 40 | 4.6 | 2 |
| 6.1 | 82% | 0 of 40 | 4.6 | 0 |

The 5.1 replies were graded by a third grader, along with 20 replies from
the other arms for calibration. That grader scored the same 6.1 replies 5
points higher than the first graders did and the default replies the same,
so 6.1's lead over 5.1 is probably a little larger than the table shows.

6.1 covers more than 5.1 and adds no factual errors, but it still drops
about 15 points against default. Most of the misses are secondary: when to
rebase rather than merge, reproducing a CI failure locally, or noting that
`avg` is correct for non-empty lists. Some aren't. No 6.1 rate-limiting plan
chose an algorithm (0 of 4), and half the process-versus-thread answers left
out isolation and race conditions. The 5.0 benchmark reported 93–94% on a
different rubric and grader, so its numbers aren't comparable with these.
