Merge vs. rebaseBoth integrate changes from one branch into another. They differ in what history they leave behind. Merge creates a new merge commit with two parents, joining the branches. Existing commits are untouched. History shows exactly what happened, including the parallel lines of work. 
      A---B---C  feature
     /         \
D---E---F---G---M  main
Rebase takes your branch's commits and replays them on top of another commit (usually the tip of main). Each replayed commit is a new commit with a new hash, even though the diff and message are the same. The old commits are abandoned. The result is a straight line. 
Before:        A---B---C  feature
              /
D---E---F---G  main

✅ Merge preserves history; rebase rewrites it. 
merge:   A-B-C-----M      rebase:  A-B-C-D'-E'
              \   /
               D-E
▸ Merge: adds a merge commit; existing commits are untouched. ▸ Rebase: replays your commits onto a new base as new commits (new hashes), so history stays linear. ▸ Dangerous on commits others already have: histories diverge, it needs a force-push, and work gets duplicated or lost. Rebase only local branches; otherwise git push --force-with-lease.
